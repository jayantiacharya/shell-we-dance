# CS 3030 Project 7 Part 1 — Proposal Grading Rubric

Total Points: 15

The proposal is graded on five criteria that map directly to the six required
sections of `PROPOSAL.md`. A strong proposal earns full credit; a
weak proposal creates risk for Part 2 and may require revision before approval.

---

## Criteria 1: Problem Statement Clarity (3 points)

*Evaluates Section 1 of the proposal.*

| Points | Level | Description |
| --- | --- | --- |
| 3 | Excellent | Problem is concrete and specific. The tool solves an identifiable pain point in a DevOps/automation context. The target user and workflow are clearly described. The justification for automation (vs. manual process) is compelling. No ambiguity about what the tool does. |
| 2 | Good | Problem is reasonably clear. Minor vagueness about the user or workflow. Automation justification present but brief. |
| 1 | Fair | Problem described at a high level but missing specifics. Automation justification absent or unconvincing. |
| 0 | Needs Work | Problem statement missing, one sentence, or describes a non-automation task. No user scenario. No justification. |

---

## Criteria 2: Technical Design Quality (5 points)

*Evaluates Section 2 of the proposal.*

| Points | Level | Description |
| --- | --- | --- |
| 5 | Excellent | Component table is complete with realistic technology choices. At least 3 technology domains checked. Data flow diagram or description shows understanding of how components interact. External dependencies listed and appropriate. No unexplained magic ("the script will just handle it"). |
| 3–4 | Good | Components described with most details. Technology domains adequate. Data flow present but may be vague. Dependencies mostly listed. |
| 2 | Fair | Components listed but with weak descriptions. Fewer than 3 technology domains. Data flow absent or unclear. Missing dependencies. |
| 0–1 | Needs Work | Technical section incomplete or incoherent. Technologies listed without any explanation of how they interact. No data flow. |

> **Penalty:** −1 point if fewer than 3 technology domains are checked.

---

## Criteria 3: Scope and Feasibility (3 points)

*Evaluates Section 3 of the proposal.*

| Points | Level | Description |
| --- | --- | --- |
| 3 | Excellent | Core features are concrete, testable, and achievable in a roughly 10-day implementation window. Stretch features are realistic extensions. Scope justification references the time available and comparable prior projects. At least 2 risks identified with plausible mitigations. |
| 2 | Good | Core features reasonably scoped. Scope justification present. 1–2 risks identified. Minor over- or under-scope. |
| 1 | Fair | Core features vague ("implement logging") or unrealistically ambitious. Scope justification weak or absent. Risks not addressed. |
| 0 | Needs Work | Core features missing or a single vague statement. No feasibility analysis. No risk assessment. |

---

## Criteria 4: Git and Collaboration Plan (2 points)

*Evaluates Section 4 of the proposal.*

| Points | Level | Description |
| --- | --- | --- |
| 2 | Excellent | Repository URL provided (even if empty). At least 4 planned feature branches with names and owners. Conventional commit format explicitly confirmed. For teams: clear work division that splits effort roughly evenly. |
| 1 | Good/Fair | Repository URL present. Some branches planned. Conventional commits mentioned. Work division described but may be incomplete or unbalanced. |
| 0 | Needs Work | Git plan missing. No branches named. No collaboration strategy for teams. |

---

## Criteria 5: Timeline and Testing Strategy (2 points)

*Evaluates Sections 5 and 6 of the proposal.*

| Points | Level | Description |
| --- | --- | --- |
| 2 | Excellent | Timeline maps work across a clear roughly 10-day span using concrete milestones and named owners. Testing strategy describes at least 2 concrete methods (e.g., pytest unit tests, integration scenario, edge case list). Definition of Done is measurable and specific. |
| 1 | Good/Fair | Timeline present with reasonable milestones. Testing approach described. Definition of Done somewhat vague or one-sentence testing strategy. |
| 0 | Needs Work | Timeline missing or a single line. No testing strategy. No Definition of Done. |
